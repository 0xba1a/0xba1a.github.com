Step 2 — Analysis
The systemd Code That Crashed
service.c — service_sigchld_event() at line 3863

The crash happens when systemd receives SIGCHLD for a service whose state says SERVICE_DEAD but still has a valid main_pid:

// src/core/service.c — systemd 255 (simplified)

static void service_sigchld_event(Unit *u, pid_t pid, int code, int status) {
    Service *s = SERVICE(u);

    if (s->main_pid.pid == pid) {
        s->main_pid.pid = 0;

        switch (s->state) {
            case SERVICE_START:
            case SERVICE_START_POST:
                /* handle start completion */  break;
            case SERVICE_RUNNING:
                /* handle process exit */       break;
            case SERVICE_STOP:
            case SERVICE_STOP_SIGTERM:
            case SERVICE_STOP_SIGKILL:
                /* handle normal stop */        break;
            default:
                assert_not_reached();       // line 3863 — CRASH
        }
    }
}
The impossible state s->state == SERVICE_DEAD yet s->main_pid.pid holds a valid PID. A dead service should never own a running process. systemd treats this as a logic error → assert_not_reached() → PID 1 crash.

Step 2b — Hypothesis
What Can Change State Without Clearing main_pid?
Searching for the unknown event that overwrites STOP_SIGTERM → DEAD
The puzzle We need an operation that:
• Overwrites a unit’s state field (e.g. STOP_SIGTERM → DEAD)
• Does not clear main_pid
• Can happen while a service is being stopped

❌ Direct state setter?

State transitions within systemd always go through service_set_state(), which clears main_pid when entering DEAD. This path is safe.

❌ Unit reload / re-read config?

Re-reading unit files updates config but does not overwrite runtime state or PID tracking. This path is safe.

⚠ Deserialization (daemon-reload)?

During daemon-reload, systemd serializes all unit states to a file, re-execs, and deserializes them back. The deserialized state is written directly to s->deserialized_state — bypassing service_set_state()!

Deserialization is the suspect Unlike normal state transitions, deserialization writes state directly into the unit object without going through service_set_state(). This means it can set a state like DEAD without the usual cleanup that would clear main_pid.
But how exactly does deserialization corrupt the state? Let’s first understand what it is.
Background
What Is Deserialization & What Is an Alias?
Understanding daemon-reload and unit aliases with a simple example
What is daemon-reload?
  1. Serialize — save every unit’s runtime state (state, PID, etc.) to a temp file
  2. Re-exec — systemd restarts itself, re-reads all unit files from disk
  3. Deserialize — restore each unit’s saved state back into memory

This lets systemd pick up config changes without stopping running services.

What is an alias?

An alias is a symlink that makes one unit reachable by a second name.

# a.service unit file:
[Install]
Alias=b.service

# "systemctl enable a.service" creates:
/etc/systemd/system/b.service → a.service

After enabling, both names point to the same unit file.

The infection path If b.service was already tracked by systemd (e.g. referenced by a socket or Wants=) with a stale DEAD state before the alias symlink was created, then daemon-reload serializes both names with divergent states. During deserialization, the alias’s DEAD overwrites the real service’s RUNNING — corrupting it.

$ ln -sf /etc/systemd/system/a.service /etc/systemd/system/b.service

$ systemctl show a.service --property=ActiveState   →  inactive  ← was RUNNING!

# Step 6: Kill PID → SIGCHLD → CRASH (DANGEROUS!)
$ kill 4567  → systemd[1]: Freezing execution.
Non-determinism: hashmap ordering Whether b is deserialized after a depends on hashmap iteration order (randomized per process). Use systemctl daemon-reexec to re-seed and retry if corruption doesn’t happen on the first attempt.
Step 3b — Debugging
Finding Which Service Was Infected
The corrupted state is transient — we need indirect evidence
Attempt 1: Add a boot script to detect the impossible state
#!/bin/bash — detect_infected_service.sh (runs at boot)
for unit in $(systemctl list-units --type=service --all --no-legend | awk '{print $1}'); do
    state=$(systemctl show "$unit" --property=ActiveState --value)
    pid=$(systemctl show "$unit" --property=MainPID --value)
    if [[ "$state" == "inactive" || "$state" == "dead" ]] && [[ "$pid" -gt 0 ]]; then
        echo "INFECTED: $unit  state=$state  main_pid=$pid"
    fi
done
Result: No infected service found after boot The corrupted state is transient — by the time the VM has fully booted, the service has likely been restarted multiple times by other scripts. The infection only exists in the brief window between daemon-reload and the next restart.
Attempt 2: Look for duplicate process detection logs
Key insight When systemd thinks a service is DEAD but then start is called again, the old process (from the infected state) is still running. systemd detects a duplicate main PID and logs an error before killing the old process. Only the second restart actually starts a fresh process. 
# Search for duplicate PID detection in journal
$ journalctl -b -1 | grep "Found left-over process"

systemd[1]: rsyslog.service: Found left-over process 1234 (rsyslogd)
            which is already a command process of rsyslog.service.
            Refusing.
Found it: rsyslog.service The “Found left-over process” log proves that when systemd tried to restart rsyslog, it found a leftover process from the corrupted state — a process systemd thought shouldn’t exist (state=DEAD) but was actually still running. This confirms rsyslog.service was the infected service.
